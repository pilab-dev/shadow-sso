# v1.1.0 — Client Credentials for Kubernetes OIDC

Released: 2026-11-03
Type: minor (backwards compatible)

`client_credentials` access tokens can now be consumed by a kube-apiserver OIDC
provider. The change adds three things a Kubernetes authenticated identity
needs — an audience, a subject, and group membership — without altering the
defaults for existing integrations.

## Highlights

### Audience (RFC 8707)

The token endpoint accepts `audience` and `resource` parameters, repeated or
space/comma separated. Accepted values are limited by the client's
`allowed_audiences`; the client's own ID is always permitted. Anything else
fails with `invalid_target`.

```sh
curl https://sso.pilab.hu/oauth2/token \
  -d grant_type=client_credentials \
  -d client_id=sa-1234@pilab.iam.sso.dev \
  -d client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer \
  -d client_assertion="$SIGNED_JWT" \
  -d audience=kubernetes
```

### Non-empty subject

`client_credentials` tokens previously carried `sub=""`. They now carry the
client identity (typically the service account email). This matters because
kube-apiserver rejects tokens without a subject and uses it as the username.

### Groups claim

A new `groups` claim is emitted for `client_credentials` tokens, sourced from
`service_account_groups` and falling back to `service_account_roles`. Kubernetes
maps it to RBAC bindings with `--oidc-groups-claim=groups`.

### `private_key_jwt` + `client_credentials` fix

The token endpoint authenticated the client, then the service validated it a
second time using a client secret that is never sent when the client uses a
client assertion. Service account keys therefore could not use
`client_credentials`. The second validation is gone; the flow works.

## Token shape

```json
{
  "iss": "https://sso.pilab.hu",
  "sub": "sa-1234@pilab.iam.sso.dev",
  "aud": ["kubernetes"],
  "exp": 1762265400,
  "iat": 1762261800,
  "jti": "…",
  "roles": ["k8s-view"],
  "groups": ["sso:k8s-view", "sso:k8s-devs"]
}
```

## Upgrade notes

- **Default behaviour is unchanged.** Without `audience`, `aud` remains
  `[client_id]`; without `service_account_groups`, `groups` mirrors
  `service_account_roles`; `sub` for user-facing grants is unaffected.
- **New client fields**: `allowed_audiences`, `service_account_groups`. Both are
  optional and stored with `omitempty`.
- **`client_credentials` clients now emit a non-empty `sub`**. Any consumer that
  relied on an empty subject for machine tokens should switch to checking
  `client_id` or a custom claim.
- **No API/CLI surface yet** for the two new fields — provision them through the
  client management API or the client document. `ssoctl` flags require a proto
  change and will follow.
- Existing tokens are unaffected; re-issue to get the new claims.

## Kubernetes setup

```
--oidc-issuer-url=https://sso.pilab.hu
--oidc-client-id=kubernetes
--oidc-username-claim=sub
--oidc-username-prefix=sso:
--oidc-groups-claim=groups
--oidc-groups-prefix=sso:
```
