# v1.2.0 — Traceability and Browser Baseline

This release makes it possible to answer, from the CLI, who is signed in from
which device, which tokens exist, and what happened in real time. It also adds
an enterprise browser baseline that blocks outdated, unpatched browsers from
interactive login.

## Highlights

### Live audit stream

`AuditService.FollowAuditEvents` is a server-streaming RPC. It replays a time
window, then tails the audit store; because it polls the persisted store, it
sees events from every replica.

```bash
ssoctl audit follow --since 15m
ssoctl audit follow --user alice@example.com --action TokenRefreshed
ssoctl audit follow --json --since 5m | jq -c .
```

New audit actions: `TokenIssued`, `TokenRefreshed`, `TokenRevoked`,
`TokenExpired`, `RefreshTokenReplay`, `SessionKicked`, `BrowserBlocked`,
`BrowserPolicyWarn`, `BrowserPolicyUpdated`, `BrowserPolicyReset`.

A background sweeper emits `TokenExpired` once per token when it crosses
`expires_at`; it does not delete or revoke anything.

### Token and device inspection

New `TokenService`:

- `ListUserTokens` — JTI, type, status (`ACTIVE`/`REVOKED`/`EXPIRED`/`ROTATED`),
  client, scope, session, refresh family, parent/rotation links, timestamps.
- `GetToken` — one token by JTI.
- `ListUserDevices` — sessions enriched with parsed browser, version, OS,
  device class, IP, last use and per-device token counts.
- `RevokeToken` — targeted revocation by JTI, with an audit reason.

```bash
ssoctl token list --all
ssoctl token get <jti>
ssoctl token revoke <jti> --reason "laptop lost"
ssoctl device list --user-id alice@example.com --all
ssoctl device show <session-id>
```

Token values are never returned or logged. The listing store is queried through
an optional `domain.TokenQueryRepository`; the MongoDB implementation supports
it, while a DTS-backed store returns `Unimplemented` for listing.

### Enterprise browser baseline

`BrowserPolicyService` stores a realm-scoped policy. It rejects interactive
logins from browsers below the configured minimum major versions, with a safe
`warn` mode for rollout.

```bash
ssoctl browser-policy show
ssoctl browser-policy check "Mozilla/5.0 ... Chrome/90.0 ..."
ssoctl browser-policy set --enabled --enforcement warn --block-bots
ssoctl browser-policy set --enforcement block --min chrome=126 --min safari=17.5
ssoctl browser-policy reset
```

Enforcement covers the web login/authorize/MFA/consent routes and
`AuthService.Login`/`Verify2FA`. Machine clients (`ssoctl`, `curl`, SDKs, health
probes) are exempt by default and are never browser-version-checked.

### Session provenance

`AuthService.Login` now records the User-Agent and client IP on the session, so
`session list`, `device list` and token listings show the actual browser/agent
instead of an empty field. Web authorization-code flows also create a session
when the code is issued, and the exchanged tokens carry its `sid`.
`SessionInfo` gained `last_used_at`, `is_revoked`, `browser`,
`browser_version`, `os` and `device_type`.

## Upgrade notes

- The proto changes are additive; existing clients keep working.
- The browser policy is disabled until an administrator enables it.
- MongoDB indexes are created best-effort at startup:
  `audit_events(timestamp)` and token indexes on `user_id+created_at`,
  `session_id`, `family` and `expires_at`. Creation failure is logged, not
  fatal.
- No token values were previously exposed, and none are exposed now.

## Known limitations

- Access tokens of a kicked device remain valid until their `exp`; refresh
  tokens and sessions are revoked immediately.
- Browser policy is realm-scoped; per-tenant policies need a multi-realm model.
- Audit follow depends on audit persistence. If the sink is down, events are
  still emitted to stdout but cannot be streamed from the store until it
  recovers.
